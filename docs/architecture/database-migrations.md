# Database migrations

TITAN uses **Alembic** on top of SQLAlchemy 2.x for every schema change. This
holds for any engine chosen in
[ADR 0006](../adr/0006-replicated-database-with-vectors.md), and whether an
engine can be driven by Alembic is one of the ADR's criteria. Until the ADR is
decided, development runs on single-node PostgreSQL with pgvector.

## Layout

```text
src/titan/migrations/
  env.py          async engine, reads TITAN_DATABASE_URL
  script.py.mako  revision template
  versions/       one file per revision, named YYYYMMDD_<rev>_<slug>.py
```

Commands (via `uv`):

```bash
uv run titan migrate                  # upgrade head
uv run alembic revision --autogenerate -m "added tracker entries table"
uv run alembic downgrade -1
```

`titan migrate` builds its Alembic configuration in code, so it also works from
the installed package in the container. `alembic.ini` is only for developers.

## Rules

- **Every schema change is an Alembic revision.** No manual DDL on any node, and
  no `metadata.create_all()` outside tests.
- **Review autogenerated revisions.** Autogenerate does not detect everything
  (renames, some constraint and index changes, extension types). Vector columns
  and indexes (`vector(n)`, HNSW/IVF indexes) are written by hand in the
  revision.
- **Keep revisions small.** One logical change per revision, named in past
  tense like commit titles.
- **Every revision has a working `downgrade()`.** When a downgrade would lose
  data, it raises an error with a clear message instead of guessing.
- **Keep data migrations apart from schema migrations.** Backfills over many
  rows go into their own revision and run in batches.
- **Test migrations in CI.** CI runs `upgrade head`, then `downgrade base`, then
  `upgrade head` again against a throwaway database, and fails if autogenerate
  still finds differences between the models and the migrated schema.

## Migrations in a peer cluster

Nodes are upgraded one at a time, so for a while nodes on different versions
share one replicated schema.

- **Only one node applies migrations.** `titan migrate` takes a cluster-wide
  lock (an advisory lock or a lease row, depending on the engine) before it
  runs `alembic upgrade`. The other nodes wait for the new revision to reach
  them through replication.
- **Expand, then contract.** A breaking change is split across releases:
  1. *Expand*: add new columns or tables, nullable or with defaults. Old code
     keeps working.
  2. Deploy code that writes both old and new shapes and reads the new one.
  3. Backfill.
  4. *Contract*: drop the old columns or tables in a later release, once every
     node runs the new code.
- **Startup check.** `titan-api` and `titan-worker` compare the database's
  Alembic revision with the revisions the code was built for. They refuse to
  start if the database is older than the code needs. A newer database is
  accepted, because expand/contract keeps it compatible.
- **Engine-specific DDL replication** (for example, how Spock replicates DDL or
  how cr-sqlite handles `ALTER` on replicated tables) is documented here once
  ADR 0006 is decided.
